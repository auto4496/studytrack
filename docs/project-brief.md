วันที่: 3 พฤศจิกายน 2026

สถานะ: DRAFT — ต้องให้สมาชิกทั้งสองคนตรวจและบันทึกการตัดสินใจ ยังไม่ใช่ SRS หรือ feature contract ฉบับสมบูรณ์

อัปเดต: มี [SRS v0.1](srs.md), [System SDS](system-sds.md) และ [integration contract](integration-contract.md) จากฝั่ง A แล้ว ให้ใช้ SRS เป็นแหล่ง IDs และอ่าน [สถานะส่งต่อ A](handoffs/member-a-status.md) ก่อนทำ mapping/contract ฝั่ง B ข้อความใน brief นี้ยังใช้เป็นบริบท

## 1. ปัญหาและผู้ใช้

นักศึกษาต้องการตั้งเป้าหมายอ่านหนังสือ บันทึกเวลาที่ทำจริง และดูว่าทำได้ตามเป้าหมายอย่างต่อเนื่องเพียงใด ผู้ดูแลกิจกรรมเตรียมแม่แบบให้เลือกใช้ โดยข้อมูลส่วนตัวของนักศึกษาแยกจากหน้าที่ดูแลแม่แบบ

ชื่อผลิตภัณฑ์ชั่วคราว: StudyTrack

หัวข้อ: 8 — Habit and Activity Tracking System

## 2. บทบาท

| บทบาท | ทำได้ | ขอบเขตข้อมูล |
|---|---|---|
| Participant / นักศึกษา | ตั้งเป้าหมาย บันทึกกิจกรรม ดูและแก้ข้อมูลของตนตามกฎ ดูประวัติและผลสรุป | เป้าหมาย รายการ และผลสรุปของตนเท่านั้น |
| Program Manager / ผู้ดูแลแม่แบบ | สร้างและจัดการแม่แบบกิจกรรม | แม่แบบส่วนกลาง ไม่มีสิทธิ์ดูหรือแก้เป้าหมาย รายการ หรือผลสรุปส่วนตัวของนักศึกษา |

ใช้ seeded demo accounts แยกบทบาท และมี Participant อย่างน้อยสองบัญชีสำหรับทดสอบ cross-user access ไม่ใช้ role selector หรือ user ID ที่ส่งจาก frontend แทน authentication

## 3. กระบวนการ Sprint 1

1. ผู้ดูแล login แล้วสร้างแม่แบบการอ่านหนังสือ เช่น อ่านวิชา CPE 334 พร้อมหน่วยนาทีและช่วงค่าที่รับได้
2. นักศึกษา login เลือกแม่แบบที่ active และตั้งเป้าหมายรายวัน เช่น 60 นาที
3. นักศึกษาบันทึกเวลาที่อ่านในวันที่อนุญาต เช่น 45 นาที
4. ระบบบันทึกลง PostgreSQL และแสดงยอด 45/60 นาที หรือความคืบหน้า 75%
5. นักศึกษาเปิดหน้ารายละเอียดใหม่แล้วเรียกข้อมูลที่บันทึกกลับจาก API
6. ระบบปฏิเสธบันทึกซ้ำในวันเดียวกัน จำนวนผิดช่วง หรือวันที่ในอนาคตตามกฎ
7. API ปฏิเสธผู้ที่ไม่ login บทบาทผิด หรือผู้ที่พยายามอ่าน/แก้รายการของคนอื่น
8. logout แล้ว session เดิมใช้เรียก protected API ไม่ได้ตาม session design

## 4. กฎที่เสนอให้ตกลงก่อนทำ

นี่เป็นการตัดสินใจของทีมที่เสนอขึ้น ไม่ใช่ตัวเลขหรือข้อบังคับทั้งหมดที่อาจารย์กำหนด

| รหัส | ข้อเสนอ |
|---|---|
| BR-01 | รุ่นนี้ใช้หน่วยนาทีเป็นจำนวนเต็ม แม่แบบกำหนด min/max ภายใน 1–1440 นาที และ min ต้องไม่มากกว่า max |
| BR-02 | เป้าหมายรายวันต้องเป็นจำนวนเต็มภายในช่วงของแม่แบบ และเริ่มได้ตั้งแต่วันที่สร้างหรือวันถัดไป |
| BR-03 | หนึ่งผู้ใช้มี active goal ต่อแม่แบบได้ไม่เกินหนึ่งรายการ |
| BR-04 | หนึ่งเป้าหมายมี daily entry ได้หนึ่งรายการต่อวันที่ท้องถิ่น การส่งซ้ำปฏิเสธโดยไม่สร้างข้อมูลเพิ่ม รวมถึงคำขอพร้อมกัน |
| BR-05 | วันที่บันทึกอยู่ตั้งแต่วันเริ่มเป้าหมายถึงวันนี้ ตาม Asia/Bangkok และจำนวนต้องอยู่ในช่วงที่กำหนด |
| BR-06 | ความคืบหน้า = actual minutes / daily target × 100 แสดงค่าที่เกิน 100% ได้ และถือว่าบรรลุเมื่อ actual >= target |
| BR-07 | ผู้ใช้จัดการได้เฉพาะข้อมูลของตน ผู้ดูแลแม่แบบไม่มีสิทธิ์พิเศษในการอ่านข้อมูลส่วนตัว |
| BR-08 | เมื่อรองรับการเปลี่ยนเป้าหมายใน Sprint 2 ให้เป้าหมายใหม่มีผลวันถัดไป เก็บเวอร์ชันเป้าหมายตาม effective date เพื่อไม่เปลี่ยนผลย้อนหลัง ต้องระบุกรณีแก้หลายครั้งก่อนมีผลใน contract |
| BR-09 | streak นับวันติดกันที่ actual >= target ของวันที่นั้น โดยตรวจตามวันท้องถิ่น ต้องระบุกฎ current streak/today-not-complete ใน contract ก่อน implementation |
| BR-10 | เมื่อรองรับปิดใช้แม่แบบ ให้ห้ามสร้างเป้าหมายใหม่จากแม่แบบนั้น ส่วนเป้าหมายเดิมยังบันทึกต่อได้ และไม่เปลี่ยนหน่วยหรือช่วงค่าของข้อมูลเดิมย้อนหลัง |

กรณีตัวอย่างสำหรับ contract: 45/60 = 75%; 75/60 = 125%; รายการซ้ำถูกปฏิเสธและจำนวนแถวไม่เพิ่ม; คำขอของ User B ต่อข้อมูล User A ไม่คืนข้อมูลส่วนตัว

## 6. สิ่งที่ไม่รวมในขอบเขตที่เสนอ

- ไม่ใช้ AI แนะนำการเรียน ไม่วิเคราะห์สุขภาพ และไม่ทำ social feed/leaderboard
- ไม่เชื่อมบริการส่ง email/SMS/push จริง ตารางเตือนเป็นข้อมูลและการแสดงผลภายในแอป
- ไม่ทำการสมัครสมาชิกเอง ลืมรหัสผ่าน หรือยืนยันอีเมลใน Sprint 1
- ไม่เปิดข้อมูลส่วนตัวให้ผู้ดูแล และไม่เพิ่มการแชร์ข้อมูลโดยไม่มีการออกแบบสิทธิ์ใหม่
- ไม่ทำหลายหน่วยกิจกรรมพร้อมกันในรุ่นแรก

## 7. ข้อเสนอด้านเทคนิค

ใช้แนวทางเดียวกับ stack ที่พบในงาน TokTickIT เพื่อใช้ความรู้เดิม: React + TypeScript + Vite, Node.js + Express + TypeScript, PostgreSQL + Prisma และ Vitest/Supertest/Playwright ต้องเลือกและตรวจเวอร์ชันจริงเมื่อเริ่ม setup

เป็นโปรเจกต์และฐานข้อมูลใหม่ ไม่มีการนำข้อมูล/secret ของ TokTickIT มาใช้เป็นข้อมูลของ StudyTrack

เสนอ server-side session ผ่าน HttpOnly cookie พร้อมกำหนด expiry/revocation, CSRF strategy และ deployment origin/cookie settings ใน System SDS ก่อนทำ auth ไม่เก็บ plaintext password และไม่ใช้บัญชี manager เป็นทางลัดข้าม ownership

การออกแบบต้องรองรับ Docker และข้อมูลถาวรบน GCP แต่ Deliverable 1 ใช้ local release ได้ การเลือกบริการ GCP รอแนวทาง Lab 5

## 8. การทดสอบและหลักฐาน

- Unit: validation/progress และภายหลัง target-version/streak/date rules
- API + database integration: persistence, session/logout, role/ownership และ concurrent duplicate entry
- Selected UI E2E: manager creates template → participant sets goal → logs reading → retrieves result; rejection and logout
- ทุก AC ต้องมี planned test ID และภายหลังเพิ่ม actual file/name, result และ tested commit
- เก็บ actual red/green evidence สำหรับ meaningful rule work ไม่เขียนผลล่วงหน้า
- ใช้ฐานข้อมูลทดสอบแยกจาก dev และ seed ข้อมูลสังเคราะห์
- ต้องกำหนด NFR ที่วัดได้จริงใน SRS เช่น protected API ไม่คืนข้อมูลส่วนตัวเมื่อไม่มีสิทธิ์; ห้ามอ้าง performance โดยไม่มี target/measurement
